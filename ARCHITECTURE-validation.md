# ARCHITECTURE.md Validation Report

## Executive summary

ARCHITECTURE.md (1390 lines) is **substantially accurate and well-maintained for the systems it describes** -- nearly every reviewed section was confirmed correct against source, and most drift is low-severity naming precision (e.g. `significance` vs "salience", "citation chain" ambiguity, closed-enum lists written with "such as"). The doc's real problem is **staleness by omission**: it predates a wave of subsystems (commits/timestamps put the doc ~May 25, with autonomy, sessions, creator-directives, activity ledger landing May 27-28) and never documents five-to-six production-wired subsystems -- most importantly an entire **autonomy/wake-source engine** (the source of the "autonomous input" the doc mentions once but never explains), a **first-class multi-session model**, **creator-directives** (a third authority pillar the doc twice promises but never delivers), the **operator Correction service** the facade advertises at line 37, and the **cross-session activity ledger**. The recurring themes of drift are therefore (1) enumeration lists that are one item short or list a closed enum as open-ended, (2) entry-point pointers aimed at barrel re-exports rather than the module holding the logic, and (3) whole new subsystems absent from a doc that otherwise reads as a complete map.

**Severity counts:** 5 high, 5 medium, 12 low (+ 1 needs-human-check, since resolved -- see below; net 0 open uncertain items). Total kept findings: 22. Dropped 4 findings whose adversarial verdict was `confirmed: false` (a self-retraction mislabeled as drift; "attention" as a missing stage; "turn-action" as a missing stage; operator-advice -- doc and code agree it is retired).

## High severity

Line 420 mentions "a user-origin or autonomous input" in passing but **never sources the autonomous input** -- there is no Autonomy section (grep `autonom` = 1 hit, that single phrase). The sibling `AGENTS.md:179` already documents `autonomy/`, underscoring the gap. -> **Add an Autonomy section**: structural wake sources (triggers + conditions) scan substrate state, dedupe via watermarks, and synthesize the autonomous input that opens a turn; the harness decides *when* to wake on structural predicates, the model decides *what to do* once woken.

## Medium severity

- **[Affective Memory]** "Retrieval uses the current turn's Working Memory mood when it is available, then falls back to the repository mood" implies a simple presence check. In reality selection is gated on the working mood being **affectively active**: `perceivedMood = workingMemory.mood ?? neutral`, `perceivedMoodActive = (|valence| + |arousal| > 0.3)`, `retrievalMood = perceivedMoodActive ? perceivedMood : moodRepository.current(sessionId)` (`src/cognition/retrieval/turn-coordinator.ts:145-150`), so a present-but-flat working mood falls back to the repository. The same 0.3 threshold also gates whether mood affects scoring at all (`computeMoodBoost` returns 0 below it, `src/retrieval/scoring.ts:124-150`). -> **Add a clause** that the Working Memory mood is used only when it carries a non-trivial (active) affective signal; an inactive/near-neutral working mood falls back to the repository mood, and the same activity threshold gates mood-congruent scoring.

- **[Frame-Anomaly Classification]** "Confirmed anomalies are recorded and quarantined" (lines 493-494) implies *every* confirmed anomaly is quarantined. There is a third disposition the section omits: `trusted_operator_control`. When a confirmed anomaly arrives in a session whose `audience_role` is `operator` AND the sender's `borg_role` is `creator`, it is **not** quarantined and produces no quarantine event (`FrameAnomalyDisposition = none|trusted_operator_control|quarantine`, `src/cognition/lifecycle/turn-phase/perception-phase.ts:24,98-108`); only `disposition === 'quarantine'` records the frame_anomaly_gate + quarantined_user_entry events (`:120-130`). -> **Add a sentence**: a confirmed anomaly from the creator in an operator-role session is treated as trusted operator control and is exempt from quarantine; all other confirmed anomalies are quarantined.

- **[Evidence Ledger]** The rendered-sections enumeration has two inaccuracies: (1) it **omits the now-first-class "Cross-Session Self Activity" section** (`addCrossSessionSelfActivitySection`, section id `cross_session_self_activity`, label "3. Cross-Session Self Activity"); and (2) it **wrongly lists Shared State as a section** -- the canonical list is 16 fixed sections ending at `prior_session_memory`, and Shared State rides on the ledger as a separate optional field (`sharedState?: SharedStateArtifact | null`), rendered by `renderSharedStateArtifact`, not as an entry section (`src/cognition/evidence-ledger/types.ts:59-131,143-154`; `builder.ts:158-178`). -> **Add "cross-session self activity"** to the rendered-sections list, and either drop "and Shared State" from the section enumeration or note that Shared State attaches to the ledger as its own field, not one of the evidence sections.

- **[Closure-Loop State]** *(verdict: adjusted missing -> drifted, medium)* The section names only two pre-emission effects of the closure classification (update discourse state; suppress later closure-only output). It **omits a third, load-bearing effect**: a closure-shaped current user turn with no substantive state delta **skips Shared State compilation for the turn**. `shouldSkipSharedStateCompile` returns reason `closure_shaped` when `currentUserClosureShaped === true` AND `currentUserHasSubstantiveStateDelta === false` (`src/cognition/lifecycle/turn-phase/shared-state-phase.ts:454-465`, reason union at `:399`); threaded from the closure phase and applied in the retrieval phase, which early-returns with `appliedOperationCount: 0` so Shared State is not recompiled (`retrieval-phase.ts:1216-1277`, trace at `:1264-1269`). - **[Corrections]** *(verdict: adjusted high -> medium)* "correction" appears 5 times but only as a generic input to Commitments/Semantic writes; there is **no description of the operator Correction primitive**, and the facade's exposed `correction` operation (line 37) is never explained. `src/correction/` is a top-level peer module: `CorrectionService` (`src/correction/service.ts`, ~1124 lines) exposes `correct(id, patch, provenance, {reason})` (operator patch -> `kind:"correction"` review item, `:811-851`), `forget(id)` (archive/revoke under manual provenance with identity-event trails, `:362-554`), `invalidateSemanticEdge(id)` (`:711-809`), `applyCorrectionReview` (routes identity-bearing records through `identityService.update*` with `throughReview:true`, `:923-1123`), plus `why`/`rememberAboutMe`/`listIdentityEvents`.
